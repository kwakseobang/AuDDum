## 요약

AuDDum(어떰)의 예외 상황 26개와 동시성 시나리오 9개를 한 문서에 모았다. 관리자 운영 시나리오 10개와 확정 정책 28건은 기능 페이지(`features/`)로 옮겼고, 이 문서는 정책이 어느 페이지에 있는지 알려 주는 색인과 남은 결정을 갖는다. 시나리오 흐름도 기능 페이지에 있다.

- 예외 상황별 응답을 한눈에 보는 요약이다. 정확한 오류 코드와 상태 코드는 API 명세의 '오류 코드 목록'이 기준이다.
- 중복 참여는 애플리케이션 검증이 먼저 거절하고, DB 유니크 제약이 최종적으로 막는다.
- 남은 결정 3건은 모두 세부 사항이며 ERD를 바꾸지 않는다.

## 1. 예외 상황과 응답

요청 검증 실패는 4xx, 서버 내부 오류는 5xx로 구분한다. 아래 표는 예외 상황별 응답을 한눈에 보는 요약이다. 정확한 오류 코드와 상태 코드는 API 명세의 '오류 코드 목록'이 기준이다.

| 예외 상황 | 응답 | 서버 처리 | 비고 |
| --- | --- | --- | --- |
| 같은 신원의 동시 참여 요청 | 1건만 201, 진 쪽은 409 | 유니크 제약으로 1건만 저장 | 2번 섹션 |
| 네트워크 재시도로 동일 요청 중복 전송 | 선택과 관계없이 409 | 저장하지 않고 거절. 클라이언트는 상세 조회로 내 선택을 확인 |  |
| 마감 직전 요청 | 서버 시각이 마감 전이면 201 | 서버 시각 기준 판단 | 서버 시각 ≥ 마감 시각이면 마감, 수신 시점에 한 번 판단 |
| 마감 직후 요청 | 409 POLL_CLOSED | 저장 없음 | 참여 기록이 없는 경우에 한함. 이미 참여한 요청은 ALREADY_VOTED 409 |
| 존재하지 않는 투표 ID | 404 POLL_NOT_FOUND | 저장 없음 | ID 형식 오류는 400 |
| 존재하지 않거나 투표에 속하지 않는 선택지 | 400 INVALID_OPTION | 투표 ID와 선택지의 소속 관계 검증 | 존재와 소속을 모두 검증 |
| 질문이 없거나 500자 초과 | 400 VALIDATION_FAILED | 저장 없음, 위반 필드 반환 | 글자 수는 유니코드 문자 단위 |
| 선택지가 1개 또는 6개 이상 | 400 VALIDATION_FAILED | 저장 없음 | 선택지는 2~5개 |
| 카테고리가 없거나 허용되지 않은 값 | 400 VALIDATION_FAILED | 저장 없음 | 허용값 7개 |
| 비회원 쿠키 없음 | 정상 처리 | 서버가 새 익명 식별자를 발급 | 첫 참여 시점에 발급 |
| 비회원 쿠키 위조·변조 | 서명 검증 실패로 무효 처리 | 새 식별자로 대체하고 시도를 기록 | 쿠키는 완전한 신원 확인이 아니다 |
| 정지 회원의 쓰기 요청 | 403 MEMBER_SUSPENDED | 요청 시점 DB 상태 확인 후 거부 | 참여·신고·생성·삭제 모두 불가 |
| 탈퇴 회원의 요청 | 401(인증 무효) 또는 403 | 로그인 상태 무효화 후 거부 | 쓰기 요청마다 DB 상태 확인 |
| 미로그인 상태의 투표 생성 요청 | 401 | 저장 없음 | 조회·참여·신고는 비회원도 가능 |
| 신고 접수된(처리 전) 투표 접근 | 200 정상 노출 | 신고만으로 노출 상태를 바꾸지 않음 | PRD 정책 |
| 숨김 처리된 투표 접근 | 일반 사용자 404, 작성자·관리자 200 | 일반 사용자에게 비공개 | 관리자만 복구 |
| 삭제된 투표 접근 | 일반 사용자 404, 작성자·관리자 200 | 일반 사용자에게 비공개 | 복구 불가 |
| DB 저장 도중 오류 | 500 INTERNAL_ERROR | 전체 롤백, 부분 저장 없음, 오류 기록 | 재시도해도 유니크 제약으로 안전해야 함 |
| 집계 값과 투표 기록의 불일치 | 기록 기준으로 계산한 값을 정상 응답 | 불일치를 오류 로그·알림으로 남김 | 사용자에게는 오류가 아니다 |
| 관리자 권한 없는 회원의 관리자 API 호출 | 403 FORBIDDEN | 요청 거부, 시도를 기록 | 미로그인은 401. 404로 숨기지 않는다. 정지·탈퇴한 관리자도 권한이 없어 같은 403 FORBIDDEN이다 |
| 이미 처리된 신고에 재조치 | 409 REPORT_ALREADY_HANDLED | 처리 시점의 신고 상태가 대기가 아니면 거부 | 동시 처리는 2번 섹션 |
| 같은 신고자의 중복 신고 | 409 | 한 건만 인정 | 투표당 1회 |
| 작성자가 아닌 회원의 투표 삭제 요청 | 공개 투표 403 FORBIDDEN, 숨김·삭제된 투표 404 POLL_NOT_FOUND | 작성자 일치를 인증 정보로 판단 | 관리자가 숨긴 투표는 작성자도 삭제 불가(403 POLL_NOT_DELETABLE) |
| 연속 생성 간격 위반 | 429 | 저장 없음 | 직전 생성 후 30초 미만이면 위반. 수치는 배포로 조정 |
| 직전과 같은 질문으로 연속 생성 | 409 | 저장 없음 | 같은 회원의 직전 투표(삭제·숨김 포함) 한 건과, 앞뒤 공백을 뺀 질문 값으로 비교(대소문자 구분). 간격 위반과 겹치면 409가 우선 |
| 소셜 인증 실패·장애 | state 불일치 400/401, 장애 502/503. 로그인 이동 중의 실패는 프런트 오류 화면(`code` 쿼리)으로 302 | 회원 미생성, 재시도 안내 | UC-05 |

## 2. 동시성·정합성

중복 참여와 집계 불일치는 애플리케이션 검증만으로 막을 수 없다. 두 요청이 동시에 "아직 참여 기록이 없다"는 사전 조회를 통과하면 둘 다 저장될 수 있기 때문이다. 그래서 역할을 나눈다.

- **애플리케이션 검증**: 빠른 거절과 친절한 오류 응답을 위한 1차 방어선이다. 마감·공개 상태·선택지 소속·회원 상태·사전 중복 조회를 수행한다.
- **DB 제약조건과 트랜잭션**: 동시 요청에서도 깨지지 않는 최종 방어선이다. 유니크 제약 위반 예외는 서버가 409로 바꾼다.

| 시나리오 | 위험 | 애플리케이션 검증 | DB 제약·트랜잭션 | 기대 결과 |
| --- | --- | --- | --- | --- |
| 같은 신원이 같은 투표에 동시 참여 | 두 요청이 사전 조회를 통과해 이중 저장 | 사전 조회로 빠른 409 | 유니크 제약 (투표, 회원) 및 (투표, 익명 식별자) | 1건만 저장, 진 쪽은 409 |
| 서로 다른 사용자가 같은 선택지에 동시 참여 | 득표 카운터를 쓰면 갱신 덮어쓰기로 득표 누락 | 없음 | 카운터 없이 투표 기록 건수로 집계 | 득표 수 = 저장된 기록 수 |
| 마감 경계의 참여 요청 | 검증 통과 직후 저장 전에 마감 시각이 지남 | 서버 시각으로 마감 판단 | 저장 트랜잭션 안에서 마감을 다시 확인하지 않음 | 수신 시점 기준으로 한 번 판단 |
| 관리자 숨김·삭제와 참여가 동시에 발생 | 숨김 직전에 접수된 참여가 저장됨 | 공개 상태 확인 | 같은 트랜잭션에서 상태 확인 | 직전에 도착한 요청은 그대로 처리. 숨겨진 투표의 결과는 노출하지 않음 |
| 회원 정지·탈퇴와 쓰기 요청이 동시에 발생 | 정지 직전에 검증된 요청이 완료됨 | 요청 시점 회원 상태 확인 | 같은 트랜잭션에서 상태 확인 | 직전에 도착한 요청은 그대로 처리 |
| 저장 성공 후 응답 유실로 재시도 | 사용자가 실패로 오인해 다시 제출 | 409. 클라이언트는 상세 조회의 `myChoice`로 화면을 맞춘다 | 유니크 제약이 이중 저장을 막음 | 이중 저장 없음 |
| 투표 생성 도중 일부만 저장 | 투표는 있는데 선택지가 없는 상태 | 입력 전체를 먼저 검증 | 투표와 선택지를 한 트랜잭션으로 저장, 오류 시 롤백 | 전부 저장되거나 전혀 저장되지 않음 |
| 같은 투표 생성 요청이 중복 제출됨 | 동일 투표가 둘 생김 | 같은 회원의 직전 동일 질문 차단 | 투표 내용은 유니크로 정의하기 어렵다 | 직전 동일 질문의 연속 생성을 서버에서 차단 |
| 같은 신고에 조치가 동시에 들어옴(더블클릭·재전송) | 조치 이력이 중복되거나 상충됨 | 상태 확인 | 신고 상태가 "접수"일 때만 처리하고, 동시 요청은 신고의 낙관적 락(`version`)으로 가린다(R-REPORT-08, 설계 결정) | 1건만 성공, 나머지 409 |
| 집계 값과 투표 기록의 불일치 | 결과 화면의 득표 수와 실제 기록이 다름 | 결과는 기록 기준으로 계산 | 카운터·캐시 값을 기록과 대조하는 정합성 점검 | 기록이 진실의 원천, 불일치는 로그·알림 대상 |

### 정합성 테스트 항목

- 같은 신원으로 다수의 동시 요청을 보낸 뒤 투표 기록이 정확히 1건인지 확인한다.
- 서로 다른 신원이 동시에 참여한 뒤 선택지별 득표 합계가 전체 참여 수와 같은지 확인한다.
- 마감 시각 직전·직후의 요청이 정해진 경계 정책대로 처리되는지 확인한다.
- 쓰기 도중 오류를 주입해 부분 저장이 남지 않는지 확인한다.
- 정지 회원이 API를 직접 호출해도 쓰기가 거부되는지 확인한다.

### 유니크 제약 설계

회원과 비회원이 같은 투표 기록 테이블에 섞여 있어 (투표, 회원)과 (투표, 익명 식별자) 제약을 따로 건다. 한쪽이 비어 있는 행(NULL)은 MySQL에서 유니크 비교에서 제외되고, 회원 ID와 익명 식별자 중 정확히 하나만 채우는 CHECK 제약으로 보완한다. 자세한 내용은 도메인 모델·ERD 문서에 있다.

## 5. 남은 결정과 후속 설계 영향

남은 결정은 모두 ERD나 API 구조를 크게 바꾸지 않는 세부 사항이다. 시점에 맞게 정한다.

| 항목 | 정하는 시점 | 내용 |
| --- | --- | --- |
| P-28 운영 세부 값 | 구현 단계 | 신고 도배 방어, 중복 시도 로그 보관 기간 (신고 상세 글자 수 상한은 임시 200으로 구현) |
| 탈퇴 시 삭제할 개인정보 범위 | 개인정보 처리방침 작성 | 탈퇴 시 삭제할 정보와 보존할 정보의 구분 |
| 허위 신고자 제재 | 운영 중 | 반복 허위 신고자 처리 방식 |

### 후속 설계에 미치는 핵심 결정

| 결정 | ERD 영향 | API 영향 |
| --- | --- | --- |
| 투표 기록의 신원 모델 | 회원 ID와 익명 식별자를 별도 컬럼으로 두고 각각 유니크를 건다 | 참여 API는 하나, 인증 정보 유무로 구분 |
| 투표 공개 상태 | 상태값 하나(공개·숨김·삭제)로 두고 모든 조회에 같은 조건 적용 | 숨김·삭제 투표 응답 규칙(일반 404, 작성자·관리자 200) |
| 마감 모델 | 마감 시각을 선택 컬럼으로 두고 마감 여부는 저장하지 않고 계산 | 마감 오류 코드 POLL_CLOSED |
