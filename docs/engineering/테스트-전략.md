## 요약

테스트를 어떻게 나누고 어떻게 확인할지 정한다.

- 테스트는 책임 분리를 따라 도메인 → 서비스 → API → 구조(ArchUnit) 순으로 각 자리에서 따로 검증한다. 같은 규칙은 가장 낮은 계층 한 곳이 전수로 확인한다.
- 테스트 DB는 H2(MySQL 모드)이고, 동시 참여만 Testcontainers의 실제 MySQL 8.4로 한 번 더 확인한다.
- 확정: H2 테스트, MockMvcTester.

## 1. 테스트 전략

테스트는 설계에서 정한 책임 분리를 그대로 따라간다. 규칙은 도메인 객체에, 흐름과 트랜잭션은 서비스에, 응답은 controller에 둔다고 정했으므로 각 자리에서 따로 검증한다.

| 계층 | 대상 | 도구와 DB | 확인하는 것 |
| --- | --- | --- | --- |
| 도메인 단위 | `Poll`, `Member`, `Vote`, `Report` | JUnit, 스프링 없이 순수 자바 | 마감 판단, 상태 전이, 선택지 소속, 논리 삭제 규칙 |
| 서비스 통합 | Command·Query 서비스 | `@SpringBootTest` 또는 `@DataJpaTest`, H2 | 트랜잭션 경계, 유니크 제약, 동시 참여 처리(진 쪽 409), 기존 참여 409 |
| API | controller, 인증·인가 필터, 오류 응답 | `MockMvcTester`, H2 | 상태 코드, ProblemDetail 형식, 쿠키 발급, 회원 상태별 접근 범위 |
| 구조 | 패키지 의존 방향 | ArchUnit | 아래 "구조 규칙" 목록 |

**구조 규칙(ArchUnit이 검사한다)**

- 순환 의존이 없다.
- 아키텍처 '애플리케이션 구조'의 다이어그램에 없는 도메인 의존은 금지한다. `support`는 도메인에 의존하지 않는다.
- 다른 도메인의 repository(`infrastructure`)를 직접 쓰지 않는다(admin도 예외 없음).
- `@WebApi`는 `infrastructure`에 의존하지 않는다.
- 서비스(`@ApplicationService`)는 `*JpaRepository`와 다른 서비스에 의존하지 않는다.
- 역할 어노테이션은 맞는 패키지(`api`, `application`)에만 둔다.
- `domain`은 가장 안쪽 레이어라 다른 레이어를 참조하지 않는다. `application`은 `api`를, `infrastructure`는 `api`·`application`을 참조하지 않는다(역방향 금지).
- `common` 패키지를 만들지 않는다.

*테스트 방침*

- 도메인 단위 테스트는 규칙을 도메인에 둔 이점이 가장 크게 드러나는 곳이다. 시각은 인자로 넘기므로 마감 경계를 시계 없이 확인할 수 있다.
- 우선순위는 참여(동시성·중복), 회원 상태·인가, 마감, 생성 검증 순이다. 관리자 기능은 정상 흐름과 권한 거절 위주로 확인한다.
- 테스트 커버리지 수치 목표는 정하지 않는다. 위 우선순위의 규칙이 빠짐없이 테스트되는지를 기준으로 한다.
- 같은 입력 모양에 값만 다른 케이스는 `@ParameterizedTest`로 합친다. 테스트는 한 가지를 확인하는 단위로 나누되, 같은 요청의 응답을 항목별로 쪼개지 않는다.

*계층별 책임 (중복을 피한다)*

같은 규칙은 가장 낮은 계층 한 곳이 전수로 확인하고, 위 계층은 연결만 본다.

| 계층 | 전수로 확인하는 것(정본) | 위 계층이 보는 것 |
| --- | --- | --- |
| 값 객체 테스트 | `PollQuestion`, `OptionContent`, `ClosesAt` 등의 경계 | `Poll` 테스트는 `Poll.create`가 값 객체를 부르는 연결만 본다. |
| 도메인 테스트(`PollTest` 등) | 도메인 규칙의 진리표 | 서비스 통합 테스트는 흐름 연결, 호출 순서, 예외 전파, 신원이 규칙으로 이어지는지만 보고 조합을 전수로 반복하지 않는다. |
| 구현 클래스 테스트 | 여러 규칙이 겹치는 흐름. 예: 참여 우선순위 "이미 참여 > 마감 > 선택지 범위"는 `VoteParticipatorTest`, 숨김·삭제 투표 열람은 `PollTest`와 `PollQueryServiceTest` | |
| controller 테스트 | 슬라이스(서비스는 목)다. 요청 매핑, 인자 전달, 응답 모양만 본다. | 입력 검증(Bean Validation), 역직렬화 오류, 오류 코드→상태 매핑은 보지 않고, 통합·체인 테스트가 이미 확인한 것도 다시 보지 않는다. |
| 체인 테스트(실제 DB를 쓰는 API) | 계층이 이어지는지와 목으로 확인할 수 없는 것(쿠키, 헤더)의 대표 시나리오만 둔다. | |

**DB: H2를 쓰되 한계를 알고 간다**

테스트 DB는 H2(MySQL 모드)로 확정했다. 실제 운영 DB는 MySQL 8.4라 동작이 어긋날 수 있는 지점이 있어 미리 적는다.

| 차이 | 영향 | 대응 |
| --- | --- | --- |
| 격리 수준과 락 방식이 다르다(InnoDB는 기본 REPEATABLE READ) | 동시 참여 테스트가 H2에서 통과해도 MySQL에서 다르게 동작할 수 있다 | 아래 "실제 MySQL로 한 번 더 확인" |
| 유니크와 NULL, CHECK 제약의 세부 동작 | 회원·익명 신원 모델이 이 제약에 의존한다 | H2에서 동일한 제약을 걸고 위반 시나리오를 테스트한다 |
| 날짜 타입·정렬·문자열 비교 규칙 | 커서 페이징이나 정렬에서 차이가 날 수 있다 | 정렬과 커서는 내부 id(숫자) 기준이라 영향이 작다 |
| H2에 없는 MySQL 전용 문법 | 네이티브 쿼리를 쓰면 H2에서 실패 | 네이티브 쿼리를 피하고 JPQL과 생성 쿼리를 쓴다 |

**실제 MySQL로 한 번 더 확인 (확정, #17)**

- 동시 참여 테스트 한 묶음은 Testcontainers의 `mysql:8.4` 컨테이너에서 돈다(`MySqlConcurrencyTestSupport`, `@ServiceConnection`).
  - 태그나 별도 Gradle task로 나누지 않아 일반 `./gradlew test`에 함께 돌고, 로컬과 CI(GitHub Actions ubuntu runner) 모두 Docker만 있으면 된다.
  - 컨테이너 기동으로 테스트 시간이 늘어나 부담이 되면 그때 분리한다.
- 경합 테스트는 스레드 10개를 동시에 출발시키고 5회 반복한다.
- 첫 배포 뒤 실제 서버에서도 같은 신원의 동시 요청을 한 번 보내 한 건만 저장되는지 확인한다.

**동시성 테스트 항목**

[동시성·중복 방지](동시성-중복-방지.md)와 각 기능 페이지의 검증 항목을 그대로 쓴다. 같은 신원의 동시 요청이 1건만 저장되는지, 서로 다른 신원의 동시 참여가 득표 합계와 맞는지, 마감 경계, 저장 중 오류 롤백, 정지·탈퇴 회원 거절, 위조 쿠키, 리프레시 토큰 재사용을 확인한다.
