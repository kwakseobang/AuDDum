# 문서 전체 리뷰에서 찾은 오류·중복·누락을 정리하고 기능 페이지를 코드에 맞춘다

## 왜 하나

문서 개편(#100~#122)을 끝내고 전체를 다시 읽었다. 옮기는 과정에서 생긴 틀린 문장과 낡은 표시가 있었고, engineering·howto·product 문서는 옮기기만 해서 같은 사실이 여러 곳에 남아 있었다. 문서 작업 절차도 한 곳에 없었다.

정리하다 두 가지를 더 정했다(사용자, 2026-10-31).

- 기능 페이지의 이력 표에 문서 작업 기록이 19행 쌓였다. 기능을 읽는 사람에게는 쓸모가 없어서, 이력에는 기능의 동작·규칙·정책·API를 바꾼 이슈만 남긴다.
- 기능 페이지는 기획 단계의 시나리오를 옮긴 것이라, 이미 구현된 기능이 실제로 그렇게 동작하는지는 오류 코드·테스트 이름·API만 확인됐다. 구현된 기능은 코드를 사실로 보고 페이지를 코드에 맞춘다.

## 무엇을 건드리나

- 고친다: `docs/`의 손으로 쓰는 문서, 02 흐름도, sketch 머리말의 `status`·`features`, `scripts/DocsCheck.java`와 테스트, 하네스의 docs 절 색인 두 줄
- 옮긴다: 카카오 로그인 그림(`아키텍처-카카오-로그인` → `인증-카카오-로그인`)
- 하지 않는다: 규칙·정책의 내용 변경, R·P·UC 번호 변경, 하네스의 절 번호 참조 정리(4단계)

중복은 정본 하나를 남기고 나머지를 링크로 바꿨다. 정본은 리뷰 때 제안한 대로다(인증=토큰·쿠키, 동시성=중복 방어, 아키텍처=마감 판단 위치, 로컬 환경=마이그레이션 규칙, 배포=운영 환경 변수, 기능 페이지 README=번호·응답 코드의 뜻).

버린 안:

- PRD의 권한 표를 지우는 안. 누가 무엇을 할 수 있는지는 제품 범위라 PRD에 남기고, 세부 동작은 07로 링크했다.
- 용어집의 enum 값 목록을 지우는 안. 한글↔영문 대응이 용어집의 일이라 남기고, 이름이 어긋난 신고 사유만 고쳤다.
- 코드와 다른 곳을 하나씩 결정받는 안. 사용자가 "코드대로 일괄 수정"을 골랐다. 버그로 보이는 것만 결과에 따로 적는다.
- 결정 기록 폴더를 지우는 안. ADR은 보류하기로 했을 뿐이라, README를 "보류"로 고치고 폴더는 남겼다.

- 버그 의심: 중복 참여 시도를 "어뷰징 분석에 쓴다"고 정했지만 누가 보냈는지 남기는 로그가 없다. 아키텍처의 "요청 단위로 추적할 수 있게" 하는 로깅(`support.logging`)도 비어 있다.
