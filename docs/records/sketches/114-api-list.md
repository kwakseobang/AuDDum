# 읽을 수 있는 API 목록을 코드에서 만든다

## 왜 하나

`openapi.json`은 기계가 읽는 파일이라 사람이 훑어보기 어렵다. 손으로 쓴 `API-명세`를 없애려면 먼저 "서버에 어떤 API가 있고 각각 어떤 오류가 나는지"를 GitHub에서 바로 읽을 곳이 있어야 한다. 정적 뷰어를 공개 주소에 올리는 안은 접근을 제한할 수 없어(관리자 API도 보인다) 하지 않았고, 저장소 권한이 접근을 지켜 주는 마크다운 문서로 한다(사용자와 정했다, 2026-10-30). 이슈 #114(코드와 어긋나지 않는 사실 문서)의 네 번째 PR이다.

## 무엇을 건드리나

- 만든다: `docs/generated/API-목록.md`(생성물), 이를 만드는 `ApiListRenderer`, `OpenApiDocTest`의 비교 하나
- 고친다: `generated/README`, `index`의 문서 지도
- 건드리지 않는다: 컨트롤러·어노테이션, `API-명세`(다음 PR), `오류-코드.md`

## 어떻게 할까

| 질문 | 결정 | 이유 |
|---|---|---|
| 무엇을 원본으로 만드나 | `openapi.json`을 만드는 같은 `/v3/api-docs` 응답. 같은 테스트 클래스가 두 파일을 비교한다 | 두 파일이 한 번의 생성으로 맞춰지고, 다시 만들 때 순서 문제가 없다 |
| 표의 칸 | API, 하는 일(`summary`), 성공 상태, 오류 코드, 기능 | 오류 코드는 `@ApiResponse` 설명에서 찾되 오류 코드 enum에 있는 이름만 인정한다. 기능 칸은 기능 페이지의 "사용하는 API" 표에서 읽어, 기획자가 API에서 기능으로 갈 수 있다 |
| 영역 순서 | 투표, 참여, 신고, 회원, 인증, 관리자 순으로 고정하고 새 영역은 뒤에 이름순 | 이름순이면 관리자가 맨 앞에 와서 일반 API를 찾기 어렵다 |
| 오류 코드 표와 합칠까 | 합치지 않는다. API 목록이 API별 오류 코드 이름을 보이고, 뜻과 상태는 [오류 코드](../../generated/오류-코드.md) 링크로 간다 | 합치면 한 문서가 길어진다. 코드의 메시지와 상태는 한 곳에서 보는 편이 낫다 |

## 어떤 순서로

1. 렌더러 작성 → 2. 생성해서 표를 눈으로 확인 → 3. 영역 순서 보정 → 4. 문서 연결 → 5. 전체 빌드와 `docs-check`

## 지킬 규칙

API를 더하거나 바꾸면 `DOCS_UPDATE=1 ./gradlew test --tests '*OpenApiDocTest'`로 `openapi.json`과 `API-목록.md`를 함께 다시 만든다. 새 API는 기능 페이지의 "사용하는 API"에도 적는다(안 하면 `docs-check`가 실패한다).

## 막아야 할 것

- 오류 코드가 빠지거나 지어지는 것: 설명에 적힌 이름 중 오류 코드 enum에 있는 것만 싣는다. 설명에 이름을 안 적은 응답은 오류로 안 보인다(어노테이션을 보강하면 채워진다).
- 기능 칸이 비는 것: `docs-check`가 "어느 기능에도 없는 API"를 이미 실패시킨다.

## 한계

- 요청·응답 필드와 API 설명 문장은 이 목록에 없다. `openapi.json`을 뷰어에 붙여 본다.
- 카카오 로그인 시작·콜백은 스프링 시큐리티가 처리해서 목록에 없다(기능 페이지 07에 있다).
