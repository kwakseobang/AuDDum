# 문서 재편 확장 1 — 둘러보기·결과 보기·신고하기 기능 페이지

## 왜 하나

1단계(#106)에서 `03-참여하기`로 양식을 시험했다. 이번에는 규칙이 적거나 단순한 세 기능으로 같은 양식이 "규칙이 거의 없는 기능"에서도 통하는지 확인하고, 해당 UC·P 정의를 옮긴다. 이슈 #109의 PR 4개 중 첫 번째다.

## 무엇을 건드리나

- 새로 만든다: `docs/features/01-둘러보기.md`, `04-결과-보기.md`, `05-신고하기.md`(각각 `.d2`, `.svg`), 이 sketch
- 옮긴다: UC-01·02·13·14, P-07·P-23(둘러보기), P-03·P-25(결과 보기), P-18(신고하기)
- 건드리지 않는다: R 정의(도메인 모델), API 명세, 코드

## 어떻게 할까

- 양식과 작성 원칙은 1단계 합의를 그대로 쓴다(쉬운 말 한 벌, 한 사실은 한 곳, 응답 코드는 `흐름`·`규칙`에만).
- 여러 기능에 걸친 정책은 옮기지 않고 `예외-정책`에 남긴다: P-01(숨김·삭제, 둘러보기·관리자 조치에 걸침), P-05(정지 회원 쓰기 불가). 각 페이지는 ID로만 가리킨다.
- 결과 공개(P-03·P-25)는 참여 응답과 상세 조회 두 곳이 같이 쓰지만 "결과가 언제 보이는가"가 하나의 주제라서 `04-결과-보기`가 정의를 갖는다. 둘러보기와 참여하기는 ID로 가리킨다.
- 흐름도에는 인증(401)·형식 오류(400, 공개 ID)를 넣지 않고 비즈니스 흐름만 둔다(1단계 결정). 신고만 요청 내용 검증(400 `VALIDATION_FAILED`)이 비즈니스 규칙이라 넣었다.
- 아직 없는 `06-관리자-조치`는 링크하지 않고 글자로만 적었다. PR 2에서 링크한다.

## 어디에 넣나

| 내용 | 위치 |
|---|---|
| 기능 페이지 3개와 흐름도 | `docs/features/` |
| 옮긴 정의의 원래 자리 | `사용자-시나리오`, `예외-정책`에 이동 안내만 남김 |

## 어떤 순서로

1. 원문(UC·P·API 명세·도메인 규칙·테스트 이름)을 읽고 페이지 초안
2. 원문 대조표로 사라진 문장이 없는지 확인
3. 원본 문서에서 옮긴 정의를 지우고 이동 안내
4. `docs-check`, `test-docs-check`로 정의 개수(P=29, OP=10, UC=17, R=60)가 그대로인지 확인

## 지킬 규칙

정의는 한 번만(`docs-check`). 기능 페이지 이력과 sketch 머리말이 서로 링크. 코드 주석에 문서 이름을 쓰지 않는다.

## 막아야 할 것

- 옮기면서 문장을 잃는 것(1단계에서 3문장을 잃었다가 되살렸다)
- 규칙 표의 테스트 이름이 실제와 어긋나는 것(수동 확인: 클래스가 있는지 `find`로 검증)
