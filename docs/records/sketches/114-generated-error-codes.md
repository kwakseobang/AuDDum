# 오류 코드 표를 코드에서 만들고 예외-응답 문서를 없앤다

## 왜 하나

`API-명세`의 오류 코드 목록(24줄)은 코드의 오류 코드 enum을 손으로 옮긴 표다. 코드가 바뀌면 조용히 낡는다. 사실은 코드가 정본이므로 표를 코드에서 만들고, 어긋나면 빌드가 실패하게 한다. 이슈 #114(3단계 생성 문서)의 첫 PR이다.

같은 PR에서 `예외-응답` 문서를 없앤다. 상황별 응답은 기능 페이지의 "이럴 때는"·규칙 표와 겹치고, 코드는 오류 코드 표가 맡아서 이 문서에만 있는 것이 거의 없었다. 읽기도 어려웠다(칸 4~5개짜리 표 두 개). 사용자가 제안했다(2026-10-30).

## 무엇을 건드리나

- 만든다: `docs/generated/오류-코드.md`(생성물), 이를 만들고 비교하는 테스트 `ErrorCodeDocTest`
- 없앤다: `engineering/예외-응답.md`. 이 문서를 링크하던 곳(`index`, `ERD`, `API-명세`, `도메인-모델`, `설계-결정`, 기능 페이지 `05`·`06`·`README`·`_양식`, `CLAUDE.md`, `auddum-conventions`)은 고쳤다
- 고친다(검사): `docs-check`의 src 문서 이름 검사가 `docs/generated/` 경로는 통과시킨다(생성기가 쓸 경로를 알아야 해서). 테스트 1개 추가. 정책 정의를 예외-응답에서 모으던 설정을 없애고, `예외-응답`을 퇴역 이름에 더했다
- 고친다: `API-명세`의 7절(표 → 생성 문서 링크), 이 표를 가리키던 `index`, `예외-응답`, `CLAUDE.md`, 하네스 3곳(`auddum-conventions`, `domain-reviewer`, `test-writer`), `generated/README.md`
- 건드리지 않는다: 오류 코드 enum 자체, 응답 형식, 소셜 로그인 실패 코드 표(API-명세 2절)

## 어떻게 할까

| 질문 | 결정 | 이유 |
|---|---|---|
| 무엇이 만들고 비교하나 | JUnit 테스트. 같으면 통과, 다르면 실패하고, 환경 변수 `DOCS_UPDATE=1`이면 파일을 다시 쓴다 | CI에 단계를 더하지 않아도 `./gradlew build`가 잡는다. 도구를 따로 만들지 않는다 |
| enum 목록을 어떻게 아나 | ArchUnit(이미 의존성)으로 `ErrorCode`를 구현한 enum을 모두 찾는다 | 새 enum을 더해도 목록을 고치지 않는다 |
| 표에 무엇을 싣나 | 코드·상태·메시지·로그 수준을 도메인(공통·회원·투표·참여·신고)별 절로 나눠 싣는다. 도메인은 enum의 패키지로 정하고, 매핑에 없는 패키지가 생기면 테스트가 실패한다 | 모두 코드에 있는 값이다. 손으로 쓴 "의미" 칸은 코드에 없어서 싣지 않고, 메시지로 갈음한다 |
| 정렬 | 절 안에서 상태 코드, 코드 이름 순 | 같은 상태끼리 모여 읽기 쉽다. 파일 순서가 바뀌어도 결과가 같다 |

이 표를 따로 둘지: 사용자와 정했다(2026-10-30). 지금은 두고, PR 3에서 API 명세를 코드에서 만들 때 엔드포인트별 오류 코드와 함께 한 문서로 합치면서 이 파일을 없앤다.

버린 안: Gradle 작업(`JavaExec`)으로 생성하고 CI에서 `git diff --exit-code`로 비교하는 안. CI 단계와 작업 정의가 따로 늘어난다. 단일 테스트는 로컬에서도 같은 방법으로 돌아간다.

## 어떤 순서로

1. 테스트를 쓰고 `DOCS_UPDATE=1`로 생성물을 만든다 → 2. 링크를 새 문서로 바꾼다 → 3. `docs-check`, `test-docs-check`, 전체 빌드 → 4. 이 sketch

## 지킬 규칙

생성물은 손으로 고치지 않는다. 오류 코드를 더하면 같은 PR에서 `DOCS_UPDATE=1`로 표를 다시 만든다(안 하면 빌드가 실패한다).

## 막아야 할 것

- 생성 도구가 enum을 빠뜨리는 것: 새 enum이 자동으로 잡히는지, 이름이 겹치지 않는지를 테스트가 본다.
- 생성물이 사람마다 달라지는 것: 정렬을 고정했고, 줄 끝과 마지막 줄바꿈을 템플릿이 정한다.
