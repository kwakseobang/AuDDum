# 가독성 기준을 정하고 모든 문서에 적용한다

## 왜 하나

문서마다 굵은 글씨가 0~129개로 제각각이었다. 줄 전체를 굵게 쓴 가짜 소제목 93곳은 목차와 링크에 잡히지 않았다. 굵은 글씨가 많은 절은 오히려 아무것도 눈에 띄지 않았다. 비개발자도 읽기 피곤하지 않게, 조사한 가독성 원칙으로 기준을 정하고 한 번에 적용한다.

## 무엇을 건드리나

- 고친다: `index.md`(번호 범례를 표로, 표기 규칙에 강조·서식 기준, 자동 검사 절 신설), `docs/`의 손으로 쓰는 문서(records·generated 제외), 기능 페이지 양식·README
- 만든다: `docs-check`의 가독성 보고(실패 안 함, `--readability`로 위치 출력)
- 하지 않는다: 규칙·정책 내용 변경, 기능 페이지 이력 추가(모양만 바뀌어서)

## 어떻게 할까

조사한 자료: NN/g 시선 추적(F자 패턴, 앞부분만 훑는다, 굵은 키워드), Google 서식 규칙(굵은 글씨는 라벨에만), Microsoft 훑어 읽기(같은 모양 반복, 키워드 앞), 토스 테크니컬 라이팅(한 문장 한 정보, 메타 담화 빼기, H4는 나눌 신호), GitHub 알림 상자(문서당 1~2개).

| 질문 | 결정(사용자, 2026-10-30) | 이유 |
|---|---|---|
| 굵은 글씨 범위 | 목록·표 칸의 머리 라벨, 절마다 핵심 문장 하나, 놓치면 사고 나는 숫자, R-ID 정의 | 아껴야 눈에 띈다. 라벨은 같은 모양으로 반복되어 훑기를 돕는다 |
| 알림 상자 | 기능 페이지의 한계는 `NOTE`, 되돌릴 수 없는 작업은 `WARNING`, 문서당 2개까지 | 많아지면 아무도 안 읽는다(GitHub 권고) |
| 가짜 소제목 | `###` 제목으로 바꾼다 | 목차·링크에 잡히고 위계가 보인다 |
| 자동 검사 | 개수만 보고한다 | 기계 기준이라 틀리게 잡을 수 있다 |
| 도메인 모델의 `**속성**`·`**행위**` | 지운다 | 바로 아래 표의 첫 칸 머리와 같은 말이다 |
| 도메인 모델의 `**규칙**` | "회원이 지키는 규칙:" 같은 한 줄로 바꾼다 | `###` 아래라 제목으로 올리면 `####`가 된다 |
| 표 칸 머리의 굵은 글씨 | 라벨로 허용한다 | `이럴 때는` 표의 상황 칸이 같은 모양으로 반복되는 라벨이다(작업 중 발견, 기준 문구를 "목록·표 칸"으로 넓힘) |

버린 안: 도메인 모델의 규칙 목록을 표로 바꾸는 안. 규칙 하나가 세 문장인 곳이 있어 "표 칸은 한두 문장" 원칙과 부딪힌다.

## 결과

- 가독성 보고: 줄 전체 굵은 글씨 93 → 0, `####` 제목 10 → 0, 굵은 글씨가 많은 절 15 → 0, 긴 문장 10 → 3
- 남은 긴 문장 3개는 값을 나열한 문장이다(카테고리 7개, 틀린 입력 목록). 나누면 오히려 읽기 어렵다.
- 알림 상자: 기능 페이지 한계 6곳(`NOTE`), 로컬 환경의 마이그레이션 수정 금지와 운영 DB 직접 수정 2곳(`WARNING`)
- "아래와 같다", "다음과 같다" 같은 말에 대한 말 6곳을 내용이 있는 문장으로 바꿨다.
- 한계: 키워드가 앞에 오는지, 같은 수준의 제목 모양이 같은지는 기계로 세지 않는다.
