# 문서 재편 시범 — 03-참여하기 이전

## 왜 하나

참여 하나를 이해하려면 시나리오, 정책, 도메인 모델, API 명세, 인증 설계서를 오가야 했다. 문서를 기능 단위로 다시 나누는 개편(#99)을 전부 하기 전에, 기능 하나로 양식과 검사가 실제로 쓸 만한지 확인한다.

## 무엇을 건드리나

- 새로 만든다: `docs/features/03-참여하기.md`(+ `.d2`, `.svg`), 이 sketch
- 옮긴다: UC-03·04·10·11·12의 시나리오 정의, P-08~12·P-24의 정책 정의
- 지운다: 시나리오 문서의 참여 Mermaid 흐름도(D2로 대체)
- 건드리지 않는다: R-VOTE 정의(도메인 모델에 둔다), API 명세, 인증 설계서, 코드

## 어떻게 할까

- UC·P 정의는 기능 페이지에 **한 번만** 둔다. 원래 자리에는 이동 안내만 남긴다. 복사해 두면 두 곳이 어긋난다.
- R-ID 정의는 도메인 모델에 남기고 기능 페이지에는 한 줄 요약과 테스트 위치만 둔다. 규칙 문장의 주인은 도메인 모델이다.
- UC는 원문의 7행 표를 그대로 옮기지 않고 `UC | 상황 | 결과 | 한계` 표 한 장으로 줄였다(UC당 한 행). 사후 조건·검증 규칙·흐름 문장은 규칙 표, 흐름도, API 명세가 같은 내용을 갖고 있어 뺐다. 그러려면 `docs-check`가 기능 페이지의 표 행(`| UC-nn |`)을 UC 정의로 인정해야 해서 고쳤다.
- 시행착오: 처음에는 원문 표를 그대로 옮겼고(칸이 길어 읽히지 않음), 다음에는 UC별 문장 목록으로 썼다(여전히 글이 많음). 사용자 지적으로 표 한 장으로 줄였다. 양식에 `시나리오`·`정책` 절을 더한 것도 합의 없이 내가 넣은 것이라 사용자에게 확인받았다.
- 글은 개발자와 비개발자 한 벌로 쓴다. 독자별로 구간을 나누면 문서가 두 벌이 되어 관리가 늘기 때문이다. 쉬운 말을 본문으로 하고 기술 용어와 ID는 괄호나 끝 칸에 붙인다(원칙은 `features/README.md`). 한눈에의 ID 목록 표는 아래 표와 겹쳐 지웠고, 규칙 표는 5칸에서 3칸(규칙 / 어긋나면 / 근거·테스트)으로 줄였다.
- 같은 사실이 여러 곳에 반복됐다("이미 참여하면 409"가 9곳). 사실마다 집을 하나로 정했다: 한계는 `한눈에`, 응답 코드는 `흐름`과 `규칙`, UC 표는 상황과 결과만. 그래서 UC 표에서 `한계` 칸과 응답 코드를 뺐다. 양식에는 필수 절(한눈에·흐름·이럴 때는·이력)과 선택 절(규칙·정책 정의·API)을 구분해 적었다.
- 흐름도는 D2 격자 배치. 검사 순서가 위에서 아래로 읽히고 실패 응답이 오른쪽에 모인다. 로그인 여부에서 회원과 비회원이 갈라져 각자의 식별·확인을 거친 뒤 합쳐진다.
- 양식에 `시나리오` 절을 더했다. 옮겨 온 UC를 둘 곳이 필요했다.
- 정책(P)과 규칙(R)이 겹쳐(P-08·R-VOTE-05 등) 한 페이지에 표가 둘이면 같은 말을 두 번 읽게 됐다. 규칙 표 하나로 읽히게 하고 정책은 `근거 정책` 칸으로 붙였으며, P 정의 행은 맨 아래 `정책 정의` 절로 내렸다(처음에는 접힌 부록으로 뒀으나 찾기 어렵다는 지적으로 펼쳤다). P가 정의 행을 가져야 `docs-check`가 정의로 세므로 정의 자체는 지우지 않았다.

## 결과

- `03-참여하기` 한 페이지에 시나리오, 정책, 흐름, 규칙 요약, 실패 응답, 테스트 위치가 모였다.
- R-VOTE-07(탈퇴 회원의 참여 기록 보존)은 대응하는 테스트가 없어 "아직 없음"으로 적었다. 후속으로 테스트를 추가할지 정한다.
- D2 SVG는 임시 글꼴로 만들었다. 글꼴과 CI의 d2 설치는 3단계에서 정한다.
- 한계: 규칙 표의 요약과 테스트 이름은 손으로 적어 코드와 어긋날 수 있다. 3단계 생성 문서(정책-테스트 추적표)가 이를 대신한다.
