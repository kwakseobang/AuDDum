# AuDDum(어떰) PRD

관련 문서: [기능 페이지](../features/README.md)

이 문서는 서비스의 목표, 대상 사용자, 범위, 지표를 담는다. 세부 정책과 시나리오는 기능 페이지가 최신이고, 이 문서와 다르면 기능 페이지를 따른다.

## 요약

AuDDum(어떰)은 선택형 투표로 연애 고민을 가볍게 나누는 서비스다. 슬로건은 "너라면, 어떰?"이다.
비회원도 투표에 참여할 수 있고, 카카오 로그인 회원은 투표를 만들 수 있다.
참여 후에만 결과가 공개되며, 한 번 낸 선택은 바꿀 수 없다.
신고는 관리자가 검토해 숨김·삭제·회원 정지로 처리한다.
서버 프로그램 하나(Spring Boot 모놀리스)로 만들어 6개월 이상 운영하는 것이 목표다.

## 1. 제품 개요

가볍게 투표하고, 다른 사람들의 선택을 통해 연애에 관한 다양한 관점을 발견하는 서비스다. 핵심 기능은 투표 생성·참여, 로그인은 카카오 계정으로 하고(OAuth), 초기 목록은 최신순이며, 운영 목표는 6개월 이상이다.

### 1.1 해결하려는 문제

사람들은 썸, 소개팅, 연락, 연애 중에 생기는 고민에 대해 다른 사람들은 어떻게 생각하는지 궁금해한다. 하지만 긴 게시글을 작성하거나 댓글 토론에 참여하는 것은 부담스러울 수 있다. 이 서비스는 고민을 짧은 선택형 투표로 만들어 누구나 쉽게 참여하고 결과를 확인할 수 있도록 한다.

### 1.2 핵심 가치

- **낮은 참여 장벽**: 비회원도 로그인 없이 투표에 참여할 수 있다.
- **다양한 관점 발견**: 나와 다른 선택이 얼마나 많은지 확인할 수 있다.
- **콘텐츠 생산**: 회원이라면 직접 투표를 만들고 다른 사람들의 참여를 유도할 수 있다.
- **지속적인 방문**: 새로운 투표가 계속 등록되면서 탐색할 이유를 제공한다.

초기에는 이 가치가 실제 사용자에게 통하는지 검증한다. 재방문이나 바이럴 효과는 아직 검증되지 않은 가설이다.

## 2. 사용자 유형과 권한

비회원은 조회와 투표 참여만, 일반 회원은 투표 생성까지 가능하다. 관리자 권한은 일반 회원 권한과 분리한다.

| 기능 | 비회원 | 일반 회원 | 정지 회원 |
| --- | --- | --- | --- |
| 투표 목록 조회 | 가능 | 가능 | 가능 |
| 투표 상세 및 결과 조회 | 가능 | 가능 | 가능 |
| 투표 참여 | 가능 | 가능 | 불가 |
| 투표 생성 | 불가 | 가능 | 불가 |
| 투표 신고 | 가능 | 가능 | 불가 |
| 관리자 기능 | 불가 | 불가 | 불가 |

관리자 계정의 생성·부여 방식은 미정(별도 보안 정책으로 정한다).

## 3. 핵심 사용자 흐름

1. **서비스 접속**: 최신 투표 목록을 확인한다.
2. **투표 선택**: 질문과 선택지 2~5개를 확인한다.
3. **선택 후 투표 제출**: 회원 또는 비회원 모두 가능하다.
4. **결과 확인**: 선택별 득표수와 득표율을 확인한다.

회원은 별도로 새 투표를 작성하고 즉시 공개할 수 있다.

## 4. 기능 요구사항

### 4.1 투표 목록

- 첫 출시에서는 최신순으로 정렬한다.
- 투표 제목, 카테고리, 참여 수 등 목록에 필요한 정보를 제공한다.
- 마감된 투표도 목록 및 상세에서 확인할 수 있다.
- 최신순·인기순 탭 추가는 미정(실제 데이터가 쌓인 뒤 인기순 산정 기준과 함께 결정한다).

### 4.2 투표 생성

- 로그인 회원만 생성할 수 있다.
- 질문은 최대 500자다.
- 선택지는 최소 2개, 최대 5개다.
- 카테고리는 필수이며 하나만 선택한다.
- MVP에서는 텍스트만 지원한다.
- 입력값 검증을 통과하면 즉시 공개한다. 관리자의 사전 승인은 요구하지 않는다.

투표는 생성 후 수정할 수 없고, 작성자는 삭제만 할 수 있다. 연속 생성 간격과 직전 동일 질문의 반복 생성을 제한한다.

카테고리는 다음 7개로 시작한다: 썸 · 소개팅 · 연락 · 연애 중 · 이별 · 연애 가치관 · 기타

### 4.3 투표 참여

- 회원과 비회원 모두 참여할 수 있다.
- 한 투표에서 한 번만 참여할 수 있도록 한다.
- 제출한 선택은 변경할 수 없다.
- 투표 제출이 성공하면 결과를 바로 확인할 수 있다.
- 마감 시간이 지난 투표에는 새로 참여할 수 없다.

중복 참여 방지는 화면이 아니라 서버에서 검증한다. DB 제약조건(같은 기록을 두 번 저장하지 못하게 DB가 막는 장치)과 트랜잭션(여러 저장을 한 묶음으로 처리하는 방식)을 함께 쓰며, 비회원은 익명 식별 쿠키를 이용한다. 쿠키를 삭제하거나 다른 기기를 이용하는 경우까지 완벽히 막을 수는 없다.

### 4.4 투표 결과

- 선택지별 득표수를 제공한다.
- 선택지별 득표율을 제공한다.
- 전체 참여 수를 제공한다.
- 결과는 서버에 저장된 투표 기록을 기준으로 계산한다.
- 짧은 의견·댓글 기능은 MVP에서 제외한다.

결과는 참여한 사람에게만 공개한다. 다만 마감된 투표는 참여하지 않은 사람도 결과를 조회할 수 있다.

### 4.5 마감 정책

- 마감 시간은 선택 입력이다.
- 마감 시간을 설정하지 않으면 계속 참여할 수 있다.
- 마감 시간이 지나면 새 투표 참여만 차단한다.
- 기존 결과는 계속 조회할 수 있다.
- 서버가 참여 요청 시 마감 여부를 검증한다.

### 4.6 신고 및 관리자 기능

신고 대상은 투표다. 신고 사유는 다섯 가지다.

- 욕설·혐오 표현
- 성희롱
- 개인정보 노출
- 광고·도배
- 기타

신고가 접수되면 관리자 검토 대상으로 등록한다. 신고 건수만으로 자동 삭제하지 않는다. 관리자는 신고를 확인하고 투표를 숨기거나 삭제할 수 있으며, 문제가 반복되는 회원은 이용 정지할 수 있다. 신고는 한 투표에 한 번만 할 수 있고 정지 회원은 신고할 수 없다. 숨김 처리한 투표는 관리자가 복구할 수 있지만, 삭제한 투표는 복구할 수 없다.

## 5. 로그인 및 회원 정책

### 5.1 로그인

- 카카오 로그인만 지원한다.
- 비회원은 조회와 투표 참여를 위해 회원가입할 필요가 없다.
- 카카오에서 제공하는 고유 식별자를 기준으로 회원을 식별한다.
- 인증 정보와 서비스 회원 정보를 분리해서 관리한다.

### 5.2 회원 상태

초기에는 다음 상태를 기준으로 설계한다.

- **ACTIVE**: 정상 이용
- **SUSPENDED**: 이용 정지
- **WITHDRAWN**: 탈퇴

정지 회원도 스스로 탈퇴할 수 있다. 탈퇴 회원이 작성한 투표는 작성자를 익명화해 유지하고 투표 기록도 보존한다. 같은 카카오 계정으로 다시 가입하면 새 회원으로 취급한다.

## 7. 초기 백엔드 설계 방향

처음부터 마이크로서비스로 분리하지 않고, Spring Boot 기반 모놀리식 구조(서버 프로그램 하나에 모든 기능을 담는 방식)로 개발한다. 멀티모듈 구성은 후보로 두고 일단 보류한다.

| 영역 | 주요 책임 |
| --- | --- |
| Member | 회원 정보 및 이용 상태 |
| Authentication | 카카오 로그인 및 인증 처리 |
| Poll | 투표 질문, 카테고리, 마감 시간, 공개 상태 |
| PollOption | 투표 선택지 |
| Vote | 투표 기록 및 중복 참여 방지 |
| Report | 신고 접수 및 처리 상태 |
| Admin | 신고 검토, 콘텐츠 관리, 회원 제재 |

초기 기술 스택은 Java 25, Spring Boot(구현 시점의 최신 안정 버전), Spring Security, Spring Data JPA, MySQL을 기준으로 한다. Redis, 메시지 큐, 별도 검색 엔진은 처음부터 도입하지 않고, 실제 성능 문제나 운영 요구가 확인되면 추가한다.

### 개발 과정에서 특히 검증할 부분

- **동시성**: 같은 투표에 동시에 여러 요청이 들어와도 중복 참여가 발생하지 않는가?
- **데이터 정합성**: 투표 기록과 결과 집계가 일치하는가?
- **권한 검증**: 정지 회원이 API를 직접 호출해 투표를 생성할 수 없는가?
- **마감 처리**: 마감 직전·직후 요청이 서버 정책대로 처리되는가?
- **조회 성능**: 투표 목록과 결과 집계 쿼리가 데이터 증가에 따라 느려지지 않는가?
- **운영 안정성**: 오류 추적, 로그, 백업 및 복구 절차가 준비되어 있는가?

이 항목들이 실제로 검증되면 단순 CRUD 프로젝트와 차별화된 백엔드 포트폴리오를 만들 수 있다.

## 8. 운영 목표 및 성과 측정

목표는 출시 자체가 아니라 최소 6개월간 실제 사용자를 확보하고, 데이터를 바탕으로 서비스를 개선하는 것이다.

| 지표 | 확인하려는 것 |
| --- | --- |
| 투표 참여 완료율 | 방문자가 실제 투표까지 완료하는가? |
| 투표별 참여 수 | 어떤 주제에 관심이 모이는가? |
| 회원의 투표 생성 수 | 콘텐츠가 사용자로부터 생산되는가? |
| 7일 재방문율 | 다시 방문할 이유가 있는가? |
| 신고 건수와 처리 시간 | 운영 정책이 적절하게 작동하는가? |
| API 오류율 및 응답 시간 | 서비스가 안정적으로 작동하는가? |

초기에는 친구와 지인 등 20~50명에게 테스트를 부탁하고, 직접 준비한 투표 20~30개로 콘텐츠 부족 문제를 줄인다. 이후 실제 지표를 보고 목표를 조정한다. 위 숫자는 초기 실험을 위한 출발점이지, 업계 표준이나 성공을 보장하는 수치는 아니다.

## 9. 6개월 운영 로드맵

1. **1개월 차: MVP 개발 및 검증**. 핵심 기능 개발, 테스트, 초기 투표 콘텐츠 준비, 소규모 사용자 테스트.
2. **2개월 차: 사용성 개선**. 참여 도중 이탈하는 지점을 찾고 투표 생성·참여 흐름을 개선한다.
3. **3~4개월 차: 콘텐츠 및 유입 확대**. 공유하기, SNS 홍보, 인기 투표 탐색 등 실제 필요성이 확인된 기능을 추가한다.
4. **5~6개월 차: 운영 안정성 및 포트폴리오 정리**. 부하 테스트, 쿼리 최적화, 모니터링, 백업·복구 검증, 실제 개선 사례 문서화.

## 10. 확정된 주요 정책

구현 전에 정해야 했던 정책은 모두 확정됐다. 세부 규칙은 [기능 페이지](../features/README.md)와 [ERD](../ERD.md)에 있다.

| 주제 | 확정 내용 |
| --- | --- |
| 투표 공개 상태 | 공개·숨김·삭제 3가지. 숨김은 관리자가 복구할 수 있고, 삭제는 복구할 수 없다. |
| 투표 생성 제한 | 연속 생성 간격을 제한하고, 직전과 같은 질문은 차단한다. |
| 수정·삭제 | 수정은 불가하고 작성자는 삭제만 할 수 있다. |
| 회원 탈퇴 | 작성 투표는 익명화해 유지하고 기록을 보존한다. 정지 중에도 탈퇴할 수 있다. |
