# 기능 페이지

기능 하나가 어떻게 동작하는지 이 폴더의 페이지 하나로 읽는다. 흐름, 규칙, 실패 응답, 테스트 위치가 한곳에 있다.

| 항목 | 내용 |
|---|---|
| 파일 이름 | `NN-기능이름.md` (스토리맵 순서) |
| 양식 | [`_양식.md`](_양식.md). 필수 절은 한눈에·흐름·이럴 때는·이력이고, 규칙·정책 정의·사용하는 API는 해당할 때만 둔다 |
| 시나리오·정책 정의 | 기능 페이지로 옮긴 UC·P 정의는 여기가 정본이다. UC는 `이럴 때는` 표의 첫 칸, P는 `정책 정의` 표의 첫 칸이 정의다 |
| 규칙과 정책 | 규칙(R)은 코드가 항상 지키는 조건이고, 정책(P)은 그렇게 정한 제품 결정이다. 규칙 정의는 도메인 모델 문서에 있고 여기는 한 문장 요약만 둔다 |
| 이력 | 이력 표와 [sketch](../records/sketches/)가 서로 링크한다(docs-check가 확인) |

## 작성 원칙

비개발자가 읽을 수 있게 쓰면 개발자도 읽을 수 있다. 독자별로 문서를 나누지 않고 한 벌로 쓴다.

| 원칙 | 내용 |
|---|---|
| 쉬운 말이 본문 | 문장은 비개발자가 읽는 수준으로 쓴다. 기술 용어는 괄호나 끝 칸에 붙인다 |
| 한 사실은 한 곳 | 같은 내용을 여러 절에 되풀이하지 않는다. 한계는 `한눈에`에만, 응답 코드는 `흐름`과 `규칙`에만 쓴다. 다른 곳은 ID로만 가리킨다 |
| ID는 뒤에 | UC·P·R 번호는 문장 끝 괄호나 맨 끝 칸에 둔다. 정의를 세는 표의 첫 칸(UC·P)만 예외다 |
| 위에서 멈춰도 됨 | 맨 위 몇 줄만 읽어도 이해되고, 내려갈수록 자세해진다 |
| 용어는 처음에 풀이 | 처음 나올 때 한 줄로 풀고, 길면 도메인 모델의 용어 정의로 링크한다 |
