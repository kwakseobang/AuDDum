# AuDDum 코드 리뷰 기준서

레시피다. 누가 언제 어떤 산출물로 리뷰하는지는 `.claude/agents/code-reviewer.md`가 정한다. 기준 ID는 `auddum-conventions` §3, 확정된 결정은 `docs/설계-결정.md`다. 이 문서는 **무엇을 어떻게 볼지**만 담는다.

## 1. 우선순위

가장 중요한 것은 **유지보수와 장애 대응에 쉬운 코드**, 그리고 **누가 봐도 알기 쉬운 코드·포맷·네이밍**이다. 지적이 상한에 걸리면 이 순서로 남긴다.

1. 장애 대응성: 장애가 났을 때 원인을 빨리 찾을 수 있는가
2. 가독성·네이밍·포맷: 처음 보는 사람이 읽고 이해하는가
3. 유지보수성: 한 곳을 바꿀 때 고칠 곳이 몇 군데인가
4. 그 밖의 영역(성능·JPA, 보안, 마이그레이션 등)

## 2. 영역별 점검 항목

diff가 건드리지 않은 영역은 보지 않는다. 조건 영역은 해당 변경이 있을 때만 켠다.

### 책임 분배 (항상)
- 로직이 맞는 계층·애그리거트에 있는가. 서비스가 도메인 규칙을 들고 있지 않은가.
- 검증·공통 조회가 `*Reader`로 빠졌는가, 컨트롤러가 얇은가.
- 다른 애그리거트의 정보가 필요한 판단은 서비스가 조합하되 규칙 자체는 도메인에 두는 방법이 있다(예: 조건을 `Supplier`로 넘기기).

### DDD·OOP (항상)
- 불변식을 도메인 객체가 지키는가. 빈약한 모델(getter로 꺼내 서비스에서 판단)은 아닌가.
- 값 객체 후보, 분기가 늘어나는 곳의 다형성, 상태 변경 메서드의 이름과 위치, 결합도·응집도.

### 일관성 (항상)
- 주변 코드와 같은 방식인가(이름, 예외, 응답 형태, JPQL, 의존 방향). 사용자 취향은 `설계-결정.md` §3과 `개발-가이드.md` §3.
- **주변 코드 3곳 이상**을 비교한 근거가 있어야 지적한다. 취향 차이면 쓰지 않는다.

### 가독성·네이밍·포맷 (항상)
- 이름이 의도를 드러내는가. 같은 개념에는 같은 이름, 약어·모호한 이름(`data`, `info`, `temp`, `process`) 지양, 도메인 용어와 일치.
- 메서드 길이와 중첩 깊이, 중복, 주석이 "무엇"이 아니라 "왜"를 설명하는가.
- 쓰이지 않는 메서드·클래스, 과한 추상화·방어 코드(YAGNI).
- 포맷: `.editorconfig`(공백 4칸·LF·한 줄 130자)와 import·빈 줄·줄바꿈 방식이 주변 코드와 같은가. 자동 포맷터가 없어 사람이 보는 항목이다.

### 장애·안정성·대응성 (항상)
- 예외 누락과 삼켜진 예외(`catch`에서 아무것도 안 함), 트랜잭션 경계(범위, 외부 호출, 읽기 전용), 동시성(락·유니크 제약·경합 응답), 멱등성과 재시도, 경계값·null 흐름.
- **장애 대응성**: 실패 시 로그에 원인과 식별자(회원·투표 ID 등)가 남는가(토큰·개인정보는 제외). 로그 레벨이 맞는가(예상된 4xx에 ERROR 금지, 예상 밖 실패는 ERROR). 예외 메시지·오류 코드로 원인을 구분할 수 있는가. 서로 다른 실패가 같은 오류로 뭉개지지 않는가. 원인 예외가 체인(`cause`)으로 이어지는가.

### 성능·JPA (항상)
- N+1, 불필요한 조회, 인덱스 사용, 지연 로딩 예외, 영속성 컨텍스트 범위.
- 엔티티를 응답으로 직접 노출, 양방향 연관, `@Modifying` 후 컨텍스트 불일치, 페이징·정렬 안정성(정렬 키 중복 시 누락·중복).

### 보안 — OWASP Top 10 범주 (항상)
해당 변경에 걸리는 범주만 본다. 번호는 판마다 달라 범주 이름으로 적는다.
- 접근 통제 실패: 소유자·관리자 확인 누락, ID 추측으로 남의 자원 접근, 존재 여부 노출(404와 403의 선택)
- 인증 실패: 토큰·쿠키 검증, 리프레시 토큰 처리, 재사용·탈취 대응
- 인젝션: JPQL 문자열 결합, 검증되지 않은 입력이 쿼리·경로·헤더로 들어가는 곳
- 암호화 실패·민감 정보 노출: 비밀값 하드코딩, 로그·응답·예외 메시지의 토큰·개인정보
- 보안 설정 오류: CORS·Origin·쿠키 속성(HttpOnly·Secure·SameSite), 환경별 기본값
- 안전하지 않은 설계: 반복 시도·레이트 리밋 부재, 비즈니스 로직 우회
- 무결성 실패: 서명 검증 생략, 신뢰할 수 없는 입력의 역직렬화
- 로깅·모니터링 실패: 권한 거절·인증 실패 같은 보안 이벤트가 기록되는가
- 취약한 구성요소: 새 의존성의 필요성과 유지 상태
- 예외 상황 처리 실패: 오류가 민감 정보를 드러내거나 보호 장치를 우회하는가

### 마이그레이션 안전성 (조건: `db/migration` 변경)
기존 데이터에서 적용되는가, 큰 테이블에서 락이 걸리지 않는가, 롤백 방법이 있는가, ERD와 일치하는가.

### API 계약 (조건: 컨트롤러·DTO 변경)
응답 필드 이름·타입이 하위 호환을 깨지 않는가, 멱등성, 오류 응답 형태. 문서와의 일치는 domain-reviewer다.

### 테스트 품질 (조건: 테스트 변경)
구현을 그대로 따라 쓴 취약한 테스트, 경계·실패 경로 부족, 시간·랜덤 의존, 픽스처 중복. 이름·구성 규칙은 domain-reviewer다.

## 3. 이 프로젝트의 예시

시범 실행과 리뷰에서 나온 사례다. 새 사례가 쌓이면 여기에 한 줄씩 더한다.

| 영역 | 나쁜 예 | 좋은 예 |
|---|---|---|
| 책임 분배 | 서비스가 `poll.isPublic() \|\| poll.isAuthor(id) \|\| memberReader.isAdmin(id)`로 열람 규칙을 조합 | `poll.isReadableBy(viewerId, () -> memberReader.isAdmin(viewerId))`로 규칙은 `Poll`에, 관리자 여부는 지연 평가로 |
| DDD·OOP | `MemberReader` 람다에 `member.isAdmin() && !member.isWithdrawn()` | `Member.hasAdminAuthority()`로 옮겨 조회는 Reader, 판단은 Member |
| 가독성 | 테스트 3곳에 같은 `ReflectionTestUtils.setField(member, "role", ...)` | `MemberFixture.createMember(Role)`로 모음 |
| 불필요한 코드 | 쓰는 곳이 없는 `MemberReader.getAdmin` | 쓰는 이슈에서 만든다 |
| 오탐 주의 | `isAuthor(null)`이 true일 수 있다는 지적 | `Long.equals(null)`은 false이고 컬럼이 NOT NULL이라 안전. 코드를 열어 확인한 뒤에 지적한다 |

## 4. 설계 제안 틀

`## 설계 제안(선택)`에 쓰고 판정에는 영향이 없다. 프로젝트 규모(MVP, 서버 1대, MySQL 단일)에 맞는 것만 낸다. 메시지 브로커·분산 락·저장소 분리는 제안하지 않는다.

```markdown
### SP-n: <제목>
- 대안: <무엇을 어떻게 바꾸는가>
- 얻는 것: <지금 코드에서 실제로 보이는 문제를 어떻게 줄이는가>
- 비용: <바꿀 곳, 테스트, 복잡도>
- 도입 시점: <지금 / 어떤 신호가 보일 때>
```

예: 도메인 이벤트로 분리(결합이 줄지만 구독자가 하나면 보류), 비동기 처리(응답 지연이 문제가 될 때), 조회자 값 객체 `Viewer`(익명 쿠키를 상세 조회에 넘기는 #15·#16에서).
