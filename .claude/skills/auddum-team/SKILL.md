# auddum-team 오케스트레이터

이슈 하나(feature 브랜치 하나)를 처리하는 동안 팀이 테스트를 먼저 쓰고, 구현 후 docs와 대조해 리뷰하고, 커밋·PR을 돕는다. 팀의 역할은 **테스트 작성과 리뷰뿐**이고, 구현(서비스·컨트롤러·도메인 모델 코드·마이그레이션)은 전부 사용자가 한다. **너(메인 스레드)가 오케스트레이터다.** 서브에이전트는 다른 서브에이전트를 띄울 수 없으므로 지휘는 반드시 여기서 한다.

핵심 품질 장치 세 가지:
1. **입력 분리.** test-writer는 구현이 아니라 docs에서 기대값을 가져오고, domain-reviewer는 docs와 diff만 본다. 구현자가 놓친 것을 서로 다른 입력으로 잡는다.
2. **도구가 최종 판정.** 에이전트가 맞다고 해도 `./gradlew build`(테스트·ArchUnit 포함)가 실패하면 실패다.
3. **토큰 절약.** 이슈 위험도에 따라 호출하는 에이전트 수를 정한다. 에이전트는 이슈의 참고 문서 절만 읽는다.

## 흐름도

```
사용자 요청 (기능 단위 = feature 브랜치 1개 = run-id 1개)
   │
[Phase 0] 사전 확인(docs/, 브랜치, run-id, _workspace gitignore) → 모드 선택
   │
   ├─ A 이슈 시작 ─→ gh issue view → 위험도 판단 → [확인 ①] 브랜치 생성 + 00_brief
   ├─ B 테스트 먼저 → test-writer → red 확인 → 20_test-writer_note
   │      (구현 후 재실행하면 통과·BUG 분류)
   ├─ C 리뷰 ─────→ build 확인 → 00_diff → domain-reviewer → 30_domain-reviewer_report
   │      FAIL → 책임별 분배(구현자·test-writer·docs) → 수정 후 새 r<k>
   │      높음 위험도 → `/code-review` 실행을 안내(사용자가 실행)
   ├─ D 커밋 ─────→ [확인 ②] 메시지 제안 → git commit
   └─ E push·PR ──→ 전제(최신 판정 비FAIL, HEAD 일치) → [확인 ③] → push → gh pr create --base develop

머지·배포·`develop → main`: 사람이 한다. 하네스 범위 밖.
```

## Phase 0 — 사전 확인 (모든 모드, 건너뛰지 말 것)

- `docs/`가 있는가. 없으면 중단한다.
- `git branch --show-current`가 `main`·`develop`이면 모드 A 외의 쓰기 모드를 진행하지 않는다.
- `.gitignore`에 `_workspace/`가 있는가. 없으면 추가를 제안한다.
- **run-id**와 기존 `00_brief` 찾기는 `references/artifact-contract.md`를 따른다. 있으면 이어 쓰고 없으면 만든다.
- **이슈 번호**는 모드 A에서 `gh issue view`로 조회한 번호나 사용자가 `#n`으로 밝힌 번호만 쓴다. 브랜치 이름·커밋 메시지에서 추측하지 않는다.

## 위험도와 호출 범위

위험도는 모드 A에서 이슈 내용으로 판단해 사용자에게 확인받고 `00_brief`에 적는다.

| 위험도 | 해당 이슈 | test-writer | domain-reviewer | `/code-review` |
|---|---|---|---|---|
| 낮음 | 설정·의존성·문서·CI, 정책이 걸리지 않는 단순 작업 | 안 함 | 안 함 | 안 함 |
| 보통 | 일반 기능(도메인 규칙·API가 있는 이슈) | 구현 **전** | 구현 후 | 안 함 |
| 높음 | 로그인·JWT·익명 쿠키(M3), 동시 참여·중복 참여(M4), 신고 조치 트랜잭션(M5) | 구현 **전** | 구현 후 | PR 직전, 사용자가 실행 |

낮음에서도 `./gradlew build`는 항상 확인한다.

## Phase A — 이슈 시작

1. `gh issue view <n>`로 제목·완료 기준·참고 문서를 읽는다.
2. 위험도와 호출 계획을 정한다.
3. **[확인 ①]** 사용자에게 한 번에 보인다: 브랜치 이름(`feature/<n>-<요약>`), 위험도와 근거, 호출 계획. 확인하면 `develop`에서 브랜치를 만들고(`references/git-workflow.md`) `00_brief.md`를 쓴다.

## Phase B — 테스트 먼저

- 위험도가 낮음이면 건너뛴다고 알린다.
- test-writer를 호출한다(입력: `00_brief.md`, 참고 문서 절). 끝나면 note의 존재와 "품질 자체 검증" 충족을 확인하고, 직접 `./gradlew compileTestJava test`를 돌려 **red**를 확인한다. 이미 통과하는 테스트가 있으면 이유를 사용자에게 보고한다.
- note의 `## 사용자 질문`·`## Objections`는 그대로 사용자에게 전달한다.
- 사용자가 구현한다. 구현이 끝나면 B를 다시 돌려(새 q<k>) 통과·실패를 분류한다. docs 기준 실패는 BUG로 보고받아 사용자에게 알린다(고치는 건 구현자).

## Phase C — 리뷰

1. `./gradlew build`를 돌린다. 실패하면 리뷰 전에 알리고 멈춘다.
2. `git diff develop...HEAD`를 `00_diff-r<k>.patch`로 저장한다.
3. domain-reviewer를 호출한다. 판정에 따라 분기한다.

| 판정 | 행동 |
|---|---|
| `PASS` | D·E로 진행 가능 |
| `PASS_WITH_FIXES` | 권고를 사용자에게 보이고 반영 여부를 묻는다. 반영하면 새 r<k> |
| `FAIL` | 차단을 책임별로 나눈다: 구현자·docs는 사용자 몫, test-writer 몫은 B를 수정 모드로 재호출한다. 고친 뒤 새 r<k> |

재시도는 최대 2라운드다. 2회 후에도 FAIL이면 중단하고 미해결 항목을 보고한다. 사용자 판단 없이 기준을 낮춰 통과시키지 않는다.

높음 위험도면 PASS 뒤에 "`/code-review`를 실행해 보세요"를 안내한다. 내장 명령이라 사용자가 실행한다.

## Phase D — 커밋

**[확인 ②]** 변경 파일 목록과 메시지 제안을 보이고 확인받는다. 메시지 형식은 `docs/개발-가이드.md` §2다. 확인 후 경로를 명시해 `git add` → `git commit`한다. 커밋 전에 `git status`로 비밀값 파일이 없는지 본다.

## Phase E — push·PR

- 전제: 최신 리뷰 판정이 FAIL이 아니고(낮음 위험도는 해당 없음), 리뷰 시점 HEAD와 현재 HEAD가 같다. 어긋나면 재리뷰를 안내한다.
- **[확인 ③]** push할 브랜치, PR 제목, 본문 요약, `Closes #n` 여부를 보이고 확인받는다.
- 확인 후 `git push -u origin <브랜치>` → `gh pr create --base develop`. 본문은 변경 내용·관련 이슈·테스트 방법·참고 문서를 담는다.
- 결과를 `40_delivery.md`에 기록하고 PR 주소를 알린다.

## 실행 규칙

1. 에이전트에게는 **파일 경로를 지시하고 내용을 프롬프트에 복붙하지 않는다.** 틀은 `references/artifact-contract.md`.
2. 에이전트는 자기 출력 파일만 쓴다. 남의 파일을 고치라고 시키지 않는다.
3. 각 Phase 후 산출물 존재를 확인한다. 확인 없이 다음 단계로 넘어가지 않는다.
4. 산출물에 `## Objections`와 `## 사용자 질문`이 있으면 사용자에게 전달한다. 조용히 넘기지 않는다.
5. 사용자 확인 지점은 ①②③뿐이다. 그 밖에 임의로 질문을 늘리지 않는다. 불분명한 것은 가장 좁은 범위로 진행하고 종료 때 알린다.
6. 구현 코드(`src/main/**`, 도메인 모델 코드, 마이그레이션 포함)는 쓰지 않는다. 사용자가 부탁해도 이 스킬의 범위가 아니라고 알린다. 팀이 쓰는 것은 `src/test/**`와 `_workspace/`뿐이다.
7. 스폰 방식: `Agent` 도구를 `name` 없이 호출한다(서브에이전트 모드).

## 에러 핸들링

| 상황 | 대응 |
|---|---|
| 에이전트 산출물이 없음 | 1회 재호출. 또 없으면 중단하고 보고 |
| `./gradlew build` 실패 | 리뷰·PR로 넘어가지 않는다. 실패 요약을 사용자에게 보고 |
| docs 내부 모순 | 한쪽을 고르지 않고 사용자 확인으로 올린다 |
| 브랜치가 `feature/`로 시작하지 않음 | push 전에 이름 변경 여부를 확인 ③에서 함께 묻는다. `hotfix/*`의 push·PR은 범위 밖이라고 알린다 |
| `gh`·`git push` 실패 | 우회하지 않고 보고한다 |
