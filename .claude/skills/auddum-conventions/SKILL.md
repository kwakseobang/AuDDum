# AuDDum 지원 규칙

test-writer, domain-reviewer, code-reviewer가 **같은 기준**을 쓰기 위한 공유 문서다. 기준이 에이전트마다 다르면 한쪽이 통과시킨 것을 다른 쪽이 차단한다.

## §1 docs 절 색인

문서는 필요한 부분만 읽는다. 이슈에 `참고 문서`가 있으면 그 부분을 먼저 본다. 경로는 모두 `docs/` 아래다.

| 주제 | 읽을 곳 |
|---|---|
| 문서 읽는 순서, 규칙의 정본, P·UC·OP 번호 범례, 문서 지도 | `index.md` |
| 기능 하나의 시나리오(UC)·정책(P)·흐름·규칙 요약·테스트 위치 | `features/NN-*.md` (01 둘러보기, 02 투표 만들기, 03 참여하기, 04 결과 보기, 05 신고하기, 06 관리자 조치, 07 로그인과 회원) |
| 용어(투표·참여·신원·숨김·삭제·정지·탈퇴) | `domain/용어집.md` |
| 회원·MemberAuth·RefreshToken 행위·규칙·상태 전이 | `domain/도메인-모델.md` "회원 애그리거트" |
| Poll·PollOption 행위·규칙·공개 상태 전이 | `domain/도메인-모델.md` "투표 애그리거트" |
| Vote 행위·규칙 | `domain/도메인-모델.md` "참여 애그리거트" |
| Report 행위·규칙·신고 상태 전이 | `domain/도메인-모델.md` "신고 애그리거트" |
| AdminAction | `domain/도메인-모델.md` "관리자 조치 애그리거트" |
| 값 객체 검증 규칙 | `domain/도메인-모델.md` "값 객체" |
| 확정 정책 P-xx | 해당 기능 페이지의 '정책 정의'(번호로 검색) |
| 예외 상황별 응답 | 해당 기능 페이지의 '이럴 때는'과 규칙 표 |
| 동시성 시나리오 | `engineering/동시성-중복-방지.md`, 기능 페이지의 '동시 요청과 경계에서 확인할 것' |
| 관리자 운영 시나리오(OP-xx) | `features/06-관리자-조치.md`의 '운영 시나리오' |
| 유스케이스 흐름(UC-01~17) | 해당 기능 페이지의 '이럴 때는' |
| API 목록(경로, 성공 상태, 오류 코드, 쓰는 기능) | `generated/API-목록.md` |
| 요청·응답 필드 | `generated/openapi.json` |
| API 공통 규칙(기본 경로, 페이징, 오류 응답 형식) | `engineering/API-공통-규칙.md` |
| 카카오 로그인 경로와 실패 코드, 재발급·로그아웃 | `engineering/인증.md` 3절 |
| 결과 공개 규칙 | `features/04-결과-보기.md`의 규칙 |
| 오류 코드와 상태 코드 | `generated/오류-코드.md` |
| 토큰·쿠키, 익명 쿠키 | `engineering/인증.md` |
| 동시성 검증 항목 | `features/03-참여하기.md`의 '동시 요청과 경계에서 확인할 것', 각 기능 페이지 규칙 표의 테스트 칸 |
| 패키지·레이어·서비스·응답 규칙, `domain` 레이어, 조회 조합 | `engineering/아키텍처.md` §2 |
| 코드 컨벤션(클래스·테스트 이름, 검증 메서드, 응답 객체, 로그, 예외) | `engineering/컨벤션.md` |
| 커밋·PR 규칙, 큰 이슈의 PR 분할, 재리뷰 기준, 문서 작업 절차(sketch·생성 문서·검사) | `howto/개발-워크플로.md` |
| 확정된 설계 결정·코드 컨벤션(리뷰에서 다시 지적하지 않음) | `engineering/설계-결정.md` |
| 테이블·제약 | `ERD.md` §4~§5 |

## §2 테스트 규칙

| 종류 | 대상 | 도구 | 확인하는 것 |
|---|---|---|---|
| 도메인 단위 | `Poll`, `Member`, `Vote`, `Report` 등 | JUnit, 스프링 없이 순수 자바 | 마감 판단, 상태 전이, 선택지 소속, 값 객체 검증 |
| 서비스 통합 | Command·Query 서비스 | `@SpringBootTest` 또는 `@DataJpaTest`, H2 | 트랜잭션 경계, 유니크 제약, 동시 요청에서 진 쪽 409 |
| API | controller, 인증·인가, 오류 응답 | `MockMvcTester`, H2 | 상태 코드, ProblemDetail 형식, 쿠키 |
| 동시성 | 같은 신원의 동시 참여 | 실제 MySQL(컨테이너) | 기록 1건, 응답 201·409 |
| 구조 | 패키지 의존 | ArchUnit | 순환·다른 도메인 repository·`common` |

- 테스트 메서드(`@Test`) 이름만 한글 서술이다. 예: `마감된_투표에는_참여할_수_없다`. `@DisplayName`은 쓰지 않는다. 내부 헬퍼 메서드, 지역 변수, 상수, 픽스처 이름은 영어로 쓴다(`savePoll`, `closedPoll`, `QUESTION`).
- 클래스 이름은 `{대상}Test`다.
- 한 테스트는 규칙 하나만 확인한다. 정상 경로와 예외 경로를 따로 쓴다.
- 예외는 `isInstanceOf(AuddumException.class).hasMessage(...)`로 확인한다. 상태 위반은 오류 코드의 메시지(`PollErrorCode.POLL_CLOSED.getMessage()`), 입력 검증 실패는 필드별 사유 문구가 메시지다. `errorCode` 필드를 꺼내 비교하지 않는다.
- 테스트 지원 클래스는 레포에 있는 것을 상속한다. 없으면 만들지 말고 사용자에게 묻는다.
- 작성 형식은 `docs/engineering/컨벤션.md`의 "테스트 작성 방식"을 따른다: `WebApiTestSupport`를 상속하고 `mvcTester.get().uri(..).assertThat().hasStatus(HttpStatus.X).apply(print()).bodyJson().hasPathSatisfying(..)` 체이닝, `var`, `{도메인}Fixture`.
- Repository 쿼리 단독 테스트는 쓰지 않는다. 서비스 통합에서 간접 확인한다.

## §3 리뷰 기준 ID

domain-reviewer는 아래 `정책-*`, `권고-*` ID만 쓴다. 표에 없는 위반은 지적하지 않고 Objections에 남긴다.

**차단** (하나라도 있으면 FAIL)

| ID | 기준 | 근거 문서 |
|---|---|---|
| 정책-차단-1 | docs의 정책·규칙에 대응하는 구현이나 테스트가 없다 | 기능 페이지의 정책 정의, 도메인-모델 규칙 |
| 정책-차단-2 | 경로·메서드·상태 코드·오류 코드가 API 목록·`openapi.json`·오류 코드 표와 다르다 | generated/ 문서 |
| 정책-차단-3 | 도메인 규칙(마감·상태 전이·선택지 소속)이 서비스나 controller에 있다 | 도메인-모델, 아키텍처 §2 |
| 정책-차단-4 | 상태 전이·enum 값·용어가 도메인 모델과 다르다 | 용어집, 도메인-모델의 각 애그리거트 |
| 정책-차단-5 | 기능 페이지에 없는 엔드포인트·필드·정책을 추가했다 | 기능 페이지의 "사용하는 API"와 정책 정의 |
| 정책-차단-6 | 동작이 바뀌었는데 관련 docs가 그대로다 | 개발-워크플로(문서 갱신 규칙) |

**권고** (PASS_WITH_FIXES)

| ID | 기준 |
|---|---|
| 권고-1 | 예외 경로 테스트가 정상 경로보다 부족하다 |
| 권고-2 | 테스트 이름·구성이 §2와 다르다 |
| 권고-3 | 코드 이름이 유비쿼터스 언어와 다르다(투표=Poll, 참여=Vote) |

**책임 결정**: 구현이 docs와 다르면 `구현자`, 테스트가 없거나 기대값이 docs와 다르면 `test-writer`, docs가 낡았거나 모호하면 `docs`(사용자 확인 필요).

### 코드 리뷰 기준 (code-reviewer)

code-reviewer는 아래 `코드-*` ID만 쓰고, 시작 전에 `docs/engineering/설계-결정.md`를 읽어 확정된 결정은 지적하지 않는다. 정책·API 일치는 위 표의 몫이고 같은 위치에는 ID를 하나만 쓴다.

**차단** (하나라도 있으면 FAIL)

| ID | 기준 | 비고 |
|---|---|---|
| 코드-차단-1 | `아키텍처.md`나 `설계-결정.md`의 규칙을 어겼다 | 근거 문서 |
| 코드-차단-2 | 구체적인 실패 시나리오(입력·상태 → 장애)를 댈 수 있는 장애 가능성 | 시나리오를 적는다 |
| 코드-차단-3 | 구체적인 공격 시나리오를 댈 수 있는 보안 취약점(OWASP Top 10 범주) | 시나리오를 적는다 |

**권고** (PASS_WITH_FIXES)

| ID | 영역 | 기준 |
|---|---|---|
| 코드-권고-1 | 책임 분배 | 로직이 맞는 계층·애그리거트에 있지 않다 |
| 코드-권고-2 | DDD·OOP | 불변식·값 객체·다형성·빈약한 모델·결합도 |
| 코드-권고-3 | 일관성 | 주변 코드 3곳 이상과 다르다 |
| 코드-권고-4 | 가독성·네이밍·포맷 | 길이·중첩·이름·중복·주석, 쓰이지 않는 코드, 과한 추상화, `.editorconfig`·주변 코드와 다른 포맷 |
| 코드-권고-5 | 성능·JPA | N+1, 불필요한 조회, 인덱스, 지연 로딩, 영속성 컨텍스트, 페이징 |
| 코드-권고-6 | 장애·안정성·대응성 | 시나리오를 대기는 어렵지만 트랜잭션·동시성·멱등성·예외 처리에 우려가 있다. 로그·예외 메시지로 원인을 찾기 어렵다 |
| 코드-권고-7 | 보안 | 공격 시나리오는 약하지만 OWASP 범주상 보강이 필요하다(하드닝) |
| 코드-권고-8 | 마이그레이션·API 계약 | 마이그레이션 안전성, 하위 호환, 멱등성 |
| 코드-권고-9 | 테스트 품질 | 취약한 테스트, 경계·실패 경로 부족, 픽스처 중복 |

설계 제안(`## 설계 제안(선택)`)은 ID가 없고 판정에 영향을 주지 않는다.

## §4 커밋·브랜치

형식은 `docs/howto/개발-워크플로.md`를 단일 기준으로 한다. 이 스킬에 복사하지 않는다 — 두 곳에 두면 어긋난다.
